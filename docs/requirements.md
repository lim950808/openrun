# openrun 요구사항 v1 (1차 범위)

- 상태: 고정 (2026-11-10). 숫자를 바꾸면 이 문서 하단 변경 이력에 적고, 이미 발행된 리포트가 참조하는 값은 소급 변경하지 않는다.
- 범위: [ADR-0001](adr/0001-first-release-scope.md)의 1차(8주). 1.5차 이후 항목은 "비범위" 절에 둔다.
- 용어는 [glossary.md](glossary.md), 지표 정의는 [metrics.md](metrics.md), 상태 전이는 [ADR-0004](adr/0004-state-transitions.md)를 따른다.

## 1. 도메인 고정값

이 숫자들이 Flyway V1 시드, k6 시나리오, 리포트 분모를 결정한다.

| 항목 | 값 | 근거 |
|---|---|---|
| 공연 | 1개 (가칭 "연말 콘서트") | Inventory 추상화의 첫 구현체는 지정석 하나면 충분 |
| 회차 | 주간 오픈런마다 1개 자동 생성 | 매주 같은 조건으로 리포트 비교 |
| 공연장 좌석 | 1,500석 = VIP 300 · R 600 · S 600 | 국내 중형 공연장 규모. 봇 10,000명 대비 경쟁률 약 6.7:1 |
| 좌석 가격 | VIP 150,000원 · R 120,000원 · S 90,000원 | 매출 손실 추정의 가격 스냅샷 |
| 1인 최대 매수 | 1회 예약당 2석, 1인당 활성 예약(HOLDING·PAYING) 1건 | 1.5차 봇 방어에서 상한 재조정 |
| 락 전략 | 5종: `NAIVE` · `FOR_UPDATE` · `SKIP_LOCKED` · `CONDITIONAL_UPDATE` · `REDIS_LUA` | M1 비교 대상. 기본 전략은 ADR-0005에서 결정 |
| hold TTL | 12분, 연장 없음. 단 결제 진행 중(PAYING + CONFIRMING·UNKNOWN)인 예약은 만료 시각이 지나도 janitor가 풀지 않는다 | 토스 승인창 10분 + 결제위젯 진입까지 2분 여유. 자세한 정합은 ADR-0004 |
| 오픈 시각 | 매주 토요일 20:00 KST | 리포트 주기와 동일 |
| 대기열 진입 허용 | 오픈 10분 전(19:50)부터 | 진입 시각 분포를 넓혀 FIFO 측정을 의미 있게 |
| 입장 속도 | 초당 100명 (기본값, 시나리오 yaml로 조정) | 좌석 API p99 목표를 지키는 범위에서 M2에서 재조정 |
| 입장 토큰 유효 | 10분. 좌석 조회·hold API에만 필요. 결제 시작·confirm·취소 API는 예약 소유자 검증으로 보호하며 입장 토큰을 요구하지 않는다 | 좌석 선택 시간. 만료 시 대기열 재진입. 결제 중 토큰이 만료돼도 결제는 이어진다 |
| 폴링 간격 | 클라이언트 2~3초, 봇 2초 | 새로고침 폭풍 시나리오는 0.2초 |
| 결제 수단 | 카드 단일 (토스 테스트 키) | 멀티 PG는 트랙 확장 |
| 취소 | 전액 취소만, 공연 시작 전까지 | 수수료·부분취소는 1.5차 |
| 회원 | 간이 회원 (닉네임 + 발급 id, 로그인 없음) | 봇은 사전 생성된 id 사용. 사람 참여는 1.5차 |

## 2. 주간 오픈런 운영 일정 (토요일, KST)

| 시각 | 동작 | 담당 |
|---|---|---|
| 10:00~13:00 | **벤치마크 실행 3회**: 격리된 러너에서 회차를 매번 새로 시드하고 같은 시나리오를 연속 3회 실행. p99·처리량·전략 비교는 여기서 나온다 | GitHub Actions `bench` 워크플로 |
| 19:00 | 다음 회차 생성, 좌석 마스터 1,500석에 hold 없음 상태로 시드 | 앱 스케줄러 |
| 19:50 | 대기열 열림, 봇 진입 시작 | GitHub Actions cron → k6 |
| 20:00 | 오픈. 입장 스케줄러 가동 | 앱 스케줄러 (ShedLock) |
| 20:30 | 봇 투입 종료 | k6 |
| 20:45 | 잔여 hold 만료 처리 완료 확인, 정합성 검증 쿼리 실행 | 검증 스크립트 |
| 22:00 | 리포트 발행: 벤치마크 3회 중앙값 + 주간 오픈런 1회 결과를 한 문서로 | GitHub Actions → `docs/reports/` |

실행은 두 종류다. **벤치마크**는 3회 연속 실행의 중앙값으로 성능 수치(p99·처리량)를 내고, **주간 오픈런**은 20:00에 1회만 돌며 운영 흐름(스케줄러·janitor·리포트 자동 발행)이 실제로 도는지를 보인다. 오버셀·레이스 같은 정합성 지표는 두 실행 모두에서 센다. 환경 규칙은 [roadmap.md](roadmap.md) "부하 테스트 환경 규칙".

## 3. 사용자 스토리와 수용 기준

ID는 테스트 이름과 리포트 각주에 그대로 쓴다. 수용 기준의 숫자는 [metrics.md](metrics.md) 정의를 따른다.

| ID | 행위자 | 시나리오 | 수용 기준 | 단계 |
|---|---|---|---|---|
| R0-1 | 개발자 | 빈 서비스를 빌드·테스트·부하 스모크까지 CI에서 돌린다 | `./gradlew build` 통과, k6 스모크 200 응답, Boot 4 게이트 항목 전부 통과 또는 Boot 3.5 전환 ADR | 릴리스 0 |
| M1-1 | 사용자 | 좌석 1~2석을 선점한다 (M1은 `X-Member-Id` 헤더로 회원을 식별하고, M2에서 입장 토큰으로 대체) | 응답에 만료 시각 포함. 같은 좌석을 두 명이 동시에 요청하면 정확히 한 명만 성공 | M1 |
| M1-2 | 시스템 | 12분이 지나면 hold가 풀리고 좌석이 AVAILABLE로 돌아온다 | 만료 후 60초 내 재선점 가능 | M1 |
| M1-3 | 개발자 | 락 전략 5종(NAIVE·FOR_UPDATE·SKIP_LOCKED·CONDITIONAL_UPDATE·REDIS_LUA)을 같은 벤치마크 시나리오로 비교한다 | NAIVE는 오버셀 재현, 나머지 4종은 오버셀 0건. 전략별 p99·처리량 표 | M1 |
| M1-4 | 사용자 | 활성 예약이 있으면 추가 hold가 거부된다 | 409 응답, 기존 hold 유지 | M1 |
| M2-1 | 사용자 | 오픈 전 대기열에 들어가 순번을 본다 | 진입 시각 순으로 순번 부여, 폴링마다 앞 인원 수 반환 | M2 |
| M2-2 | 시스템 | 오픈 후 초당 N명씩 입장시키고 입장 토큰을 발급한다 | 입장 토큰 없이 좌석 API 호출 시 401. 토큰 검증은 Redis 조회 없이 | M2 |
| M2-3 | 사용자 | 새로고침을 반복해도 순번이 유지된다 | 0.2초 폴링 봇 1,000명 투입 시 순번 증가 0건, FIFO 위반률 1% 이하 | M2 |
| M2-4 | 사용자 | 입장 토큰이 만료되면 대기열 뒤로 재진입한다 | 만료 토큰으로 좌석 API 401, 재진입 시 새 순번 | M2 |
| M3-1 | 사용자 | hold한 좌석을 토스 결제위젯으로 결제하고 확정받는다 | 토스 테스트 결제 DONE → 예약 CONFIRMED, 좌석 SOLD. 실연동 영상 | M3 |
| M3-2 | 공격자 | 클라이언트 금액을 바꿔 confirm을 호출한다 | 서버 금액 불일치로 confirm 호출 안 함, 400 응답, payment는 REQUESTED 유지, hold 유지 | M3 |
| M3-3 | 사용자 | hold가 만료된 뒤 confirm을 시도한다 | confirm 호출 안 함, payment FAILED · 예약 EXPIRED 연쇄, 좌석 재선택 안내. 토스 결제는 미승인 상태로 자동 만료 | M3 |
| M3-3b | 시스템 | confirm 호출 중에 hold 만료 시각이 지난다 | 좌석은 PAYING 동안 HELD로 유지되어 다른 회원이 잡지 못하고, 응답이 오면 CONFIRMED. 오버셀 0건 | M3 |
| M3-4 | 시스템 | confirm 응답이 타임아웃된다 | payment UNKNOWN, janitor가 60초 내 재조회해 CONFIRMED 또는 FAILED 확정 | M3 |
| M3-5 | 시스템 | 토스 조회가 5분 이상 실패해 좌석을 풀었는데 그 뒤 승인이 확인된다 | janitor가 60초 내 토스 취소 호출, `confirm_expire_race_remaining` 0건 | M3 |
| M3-6 | 토스 | 웹훅이 중복·역순·지연으로 온다 | 서명 검증, eventId 중복 폐기, 과거 상태 폐기, 1초 내 200 응답 | M3 |
| M3-7 | 사용자 | 같은 confirm 요청을 두 번 보낸다 | Idempotency-Key로 토스에 1회만 전달, 두 응답 동일 | M3 |
| M3-8 | 사용자 | 확정된 예약을 공연 전 전액 취소한다 | payment CANCELLED, 좌석 AVAILABLE 복귀 | M3 |
| M4-1 | 사용자 | 대기열·좌석맵·결제결과 3페이지를 브라우저로 쓴다 | 상태별(대기·만료·실패) 화면 존재, 모바일 폭에서 깨지지 않음 | M4 |
| M4-2 | 운영자 | 주간 오픈런이 사람 손 없이 돌고 리포트가 발행된다 | 토요일 22:00 `docs/reports/YYYY-MM-DD.md` 자동 커밋 | M4 |

## 4. 비기능 요구사항

고정 환경(GitHub Actions `ubuntu-latest` 또는 고정 VM)에서 3회 중앙값 기준.

| 항목 | 목표 | 측정 |
|---|---|---|
| 오버셀 | 0건 | 실행 후 검증 쿼리 (metrics.md `oversell_count`) |
| 승인·만료 레이스 잔존 (`confirm_expire_race_remaining`) | 0건 (보상 실패 건은 `compensation_failed_count`로 분리 보고) | janitor 완료 후 검증 쿼리 |
| hold API p99 | 200ms 이하 (벤치마크 M1 시나리오: 대기열 없이 hold 요청 도착률 peak 3,000 rps) | k6 `http_req_duration` |
| hold API p99 (대기열 있음) | 200ms 이하 (주간 오픈런: hold 요청률은 입장 속도 100명/초에 묶임, 폴링 포함 총 요청률 peak 약 3,000 rps) | k6 |
| 대기열 순번 API p99 | 100ms 이하 | k6 |
| 웹훅 응답 | 1초 이내 200 (토스 제한 10초) | 앱 로그 |
| UNKNOWN 체류 | 60초 이내 확정 | janitor 로그 |
| 데이터 보존 | 회차별 이벤트 원본 영구 보존 (2차 마트 입력) | outbox 테이블 |
| 비밀 관리 | 토스 키는 GitHub Secrets·로컬 `.env`만. 레포에 키 없음 | gitleaks CI |

## 5. 봇 시나리오 파라미터 (초기값)

`load/scenarios/weekly-default.yaml`(주간 오픈런)과 `load/scenarios/bench-m1-hold.yaml`(벤치마크)에 공개한다. 이 값이 2차 복원 검증의 정답이다. 복원 검증 대상은 회원 단위 확률로만 정의한다(폴링 1회당 확률 같은 과정 파라미터는 누적값을 예측하기 어려워 정답으로 쓰지 않는다).

| 파라미터 | 값 |
|---|---|
| 가상 사용자 | 10,000 |
| 총 요청 도착률 (주간) | 19:50부터 선형 증가, 20:00 peak 3,000 rps(폴링 포함), 20:05까지 유지 후 감소 |
| hold 요청 도착률 (벤치마크 M1) | 대기열 없이 peak 3,000 rps, 2분 유지 |
| 대기열 이탈 확률 | 회원당 15%. 진입 시 이탈 여부를 결정하고, 이탈 시각은 자신의 대기 시간 안에서 균등 분포 |
| 좌석 선택 시간 | 균등 10~90초 |
| 결제 포기율 | 12% (결제위젯 진입 후 이탈) |
| 결제 소요 시간 | 정규 평균 60초·표준편차 20초 |
| 매크로 비율 | 5% (좌석 선택 1초, 폴링 0.2초, 1.5차 봇 방어 대상) |

행동 분포의 출처와 한계는 [ADR-0002](adr/0002-synthetic-data-limits.md).

## 6. 1차 비범위

| 항목 | 단계 |
|---|---|
| 취소수수료, 부분취소, 대기자 승계 | 1.5차 |
| janitor 확장: 보상 취소 실패 재시도 큐, 다중 인스턴스 ShedLock, 승계 트리거 (1차 janitor는 hold 만료·UNKNOWN 재조회·보상 취소 3경로를 단일 인스턴스로 구현) | 1.5차 |
| 봇 방어 (Turnstile·ALTCHA, 지문, 1인당 hold 상한 강화) | 1.5차 |
| 사람 참여 오픈런 데이, `human` 라벨 | 1.5차 |
| CDC·마트·리니지·복원 검증 | 2차 |
| AI 브리핑·평가 하네스 | 3차 |
| 비지정석, 식당 시간 슬롯, 멀티 PG, 로그인·소셜 인증, 알림 | 선택 또는 제외 |
