## 읽는 법

- **플릿 편차.** `ubuntu-latest`가 AWS 또는 Azure 플릿에 배정되는 것을 통제할 수 없다. aws 잡은 시도율이 계획 2,786 rps에 붙고(2,760) `dropped_iterations`가 3회 합 0.6~1.2만이다. azure 잡은 시도율 1,735, `dropped_iterations` 3회 합 37~39만(계획 33.4만/회의 38%)으로 k6가 도착률을 못 지켰다. 지난 1~3차 실행도 모두 azure 커널이었고 2차(2,500~2,730 rps)만 포화가 덜했다. 같은 플릿 안에서도 편차가 있다.
- **목표 판정은 포화하지 않은 잡에서만.** azure 잡의 DB 전략 p99 255~308ms는 생성기 포화 상태의 숫자라 목표 200ms와 비교하지 않는다. 전략 순위는 두 잡에서 같다(아래).
- **성공 처리량은 상한에 붙어 있다.** 1,500석 / TTL 10초가 재고 순환 상한이라 다섯 전략이 99~105/s에 몰린다. 전략을 가르는 것은 p99와 커넥션 대기다.

| 2. p99 ≤ 200 중 성공 처리량 최고 | FOR_UPDATE 104.5 = CONDITIONAL_UPDATE 104.5 > SKIP_LOCKED 103.4 > REDIS_LUA_OUTSIDE_TX 99.3. REDIS_LUA 479.7ms 탈락 | p99 모두 200 초과(포화) → 처리량 순위만: CONDITIONAL_UPDATE 92.3 > FOR_UPDATE 92.0 > SKIP_LOCKED 90.8 = REDIS_LUA_OUTSIDE_TX 90.8 > REDIS_LUA 90.5 |
| 3. 동률이면 DB 전략 우선 | **CONDITIONAL_UPDATE** | **CONDITIONAL_UPDATE** |

`REDIS_LUA_OUTSIDE_TX`는 aws 잡에서 p99 45.8ms로 최저(DB 전략의 절반), Hikari 대기 최대 0, `dropped_iterations` 147. 성공 처리량은 −5%(추정 원인은 ADR-0005 §8). azure 잡에서는 REDIS_LUA 1,022 → 484ms로 3차 실행과 같은 그림. 남기되 기본 후보는 아니다(ADR-0005 §8).
