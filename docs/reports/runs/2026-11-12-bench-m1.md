## 3차 실행 (2026-11-16 KST, 커밋 7bf9821, run 43885613199) — `REDIS_LUA` 대 `REDIS_LUA_OUTSIDE_TX`

- https://github.com/lim950808/openrun/actions/runs/43885613199. ADR-0005 §7 변형의 첫 비교. `strategies=REDIS_LUA,REDIS_LUA_OUTSIDE_TX`, 3회, 한 잡에서 번갈아 실행했으므로 두 전략은 같은 러너 조건이다. 다른 네 전략은 돌리지 않았다
- **§6 가설 확인.** 같은 잡 안에서 Redis 판정을 트랜잭션 밖으로 옮기자 hold p99 1,100ms → 520ms(절반), Hikari 커넥션 대기 p99 487ms → 117ms, 대기 최대 171 → 43건, 시도 처리율 1,599 → 2,020 rps, `dropped_iterations` 43만 → 28만. 오버셀은 둘 다 0(도착률·버스트). 병목은 Redis 자체가 아니라 **DB 트랜잭션 안의 Redis 왕복이 커넥션을 붙잡는 것**이었다
- **이 잡의 절대값은 2차와 비교하지 않는다.** 같은 코드의 REDIS_LUA가 2차 506ms에서 이번 1,100ms로, 시도 처리율은 2,510에서 1,599로 떨어졌다. 러너 VM 편차가 2배에 이르므로 전략 비교는 반드시 같은 잡 안에서만 한다. 변형이 DB 전략(2차 161~194ms)과 어디에 놓이는지는 토요일 bench-m1이 여섯 전략을 한 잡에서 돌릴 때(리포트 #1) 본다
- 단계 표 읽을 때 주의: 변형의 `claim` p99 419ms가 `total` p99 184ms보다 큰 것은 모집단이 달라서다. 변형은 요청의 95%가 Redis에서 `SEAT_TAKEN`으로 끝나 트랜잭션을 열지 않으므로 `total`의 p99는 전체 요청 기준이고, `claim`·`reserve_insert`·`seats_insert`는 트랜잭션에 들어간 4.5%만의 분포다. 두 전략의 공정한 비교는 k6 `hold_p99_ms`와 `hikari_acquire_p99_ms`·`hikari_pending_max`다
- 변형의 비용: `id_alloc`(오토커밋 `nextval`) p99 88ms. 요청마다 커넥션을 두 번 받으므로 풀이 포화되면 이 왕복도 줄을 선다. 앱 쪽 id 생성(시퀀스 블록 캐시 등)으로 없앨 수 있지만 §5-3 기준상 DB 전략이 우선이라 실험 범위 밖
- `HoldExpiryJanitor` 수정(커밋 299478c)이 함께 들어갔다: HOLDING 만료 sweep의 `RETURNING sh.reservation_id`가 UPDATE 뒤 값(null)을 돌려줘 `freed`가 늘 false였고, 만료 시 Redis 키 삭제가 한 번도 실행되지 않았다. REDIS_LUA는 키 TTL이 `expires_at`와 같아 드러나지 않았고, 변형의 +1초 여유에서 테스트가 잡아냈다. `returning e.id as old_reservation_id`로 고쳤다. 재현 테스트는 에이전트가 변형의 janitor 테스트를 매개변수화하며 썼으므로 CLAUDE.md 규칙 5에 따라 사람이 다시 쓸 후보
